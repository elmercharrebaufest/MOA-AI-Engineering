## 1. Objective

Convertir lo construido en G3.3-G4.4 en un **producto interno adoptable** — no repetir
fases anteriores, sino cerrar la brecha entre "existe el modelo" y "un equipo nuevo puede
usarlo sin el arquitecto".

## 2. Product Definition

**`MOA-AI-Engineering` es el modelo base de AI Engineering de MOA** — no un repositorio de
documentación sobre IA, ni un catálogo de ejemplos. Es una capacidad interna que los
equipos consumen, adaptan, ejecutan, evalúan, miden y mejoran dentro de su propio SDLC.

- **Propósito**: convertir el uso heterogéneo de IA que MOA ya tiene en una práctica
  sistemática, reutilizable, gobernada y medible (`../../../strategy/vision.md`, sin cambios).
- **Usuarios**: (1) equipos consumidores (DataAgro, MOA Operaciones, Scato Puerto, Scato
  Logística, Orquestador, y equipos futuros) — consumen el Registry y el Golden Path; (2)
  quien gobierna el Common Core — hoy sin confirmar (Blocked #1), rol de facto ocupado por
  el Solutions Architect de esta iniciativa.
- **Problemas que resuelve**: (a) descubrir qué ya existe antes de reinventarlo; (b)
  estructurar cómo se prueba/mide una capacidad de IA, no solo cómo se construye; (c) dar
  un camino de promoción de Team-Specific a Common Core con evidencia, no por antigüedad
  ni repetición.
- **Qué ofrece hoy**: un Registry con 3 capacidades reales evidenciadas; 1 Golden Path
  endurecido con 1 ejecución real; 3 contratos operativos (Evidence/Evaluation/
  Measurement); un Adoption Kit; un modelo de gobierno y de riesgo proporcional.
- **Qué NO ofrece hoy**: ninguna capacidad `Corporate Standard: Y`; ninguna plataforma,
  automatización, base de datos, ni servicio; ningún evaluador/aprobador confirmado
  (Blocked #1) — la promoción real todavía depende de una decisión organizacional.
- **Common Core / Team Adaptation**: ver `operating-model.md` (sin cambios de fondo) y
  `adoption/team-adaptation.md` (versión práctica, nueva en G4.5).
- **Lifecycle**: `lifecycle.md` — sin cambios, con 1 ejemplo real de capacidad en estado
  `Pilot` con `Real Use Status: EXECUTED` (CAP-002).
- **Governance**: `security-governance.md` + `governance/` — sin cambios de fondo; ver
  sección 17 para el hallazgo externo nuevo sobre MCP de Atlassian.
- **Adoption / Contribution**: formalizados operativamente en esta fase — secciones 7, 8,
  15.
- **Ownership conceptual**: `REQUIRES VALIDATION` en todo el producto — Blocked #1 sigue
  siendo la restricción estructural más importante, confirmada otra vez en G4.4.
- **Evolución**: vía el Contribution Model (sección 15) — no hay un roadmap de producto
  fijo más allá de resolver las decisiones bloqueadas.

- **Proponer**: cualquier equipo, sin aprobación previa (autoservicio real, ya
  confirmado como PASS en el Product Test).
- **Evaluar**: idealmente alguien distinto del actor — hoy `REQUIRES VALIDATION`.
- **Adaptar**: el equipo original o cualquier adoptante, respetando `team-adaptation.md`.
- **Versionar**: campo `Version` del Registry + `Last Review` — sin versionado semántico

- **Mantener**: `Maintainer` — `REQUIRES VALIDATION` en las 3 entradas actuales, sin

- **Retirar**: `Lifecycle State: Deprecate` con justificación explícita, nunca por

## 17. Governance

Sin cambios de fondo. **Hallazgo externo nuevo (FASE 14, EXTERNAL EVIDENCE)**: la
documentación oficial de Atlassian confirma que el **Rovo MCP Server usa OAuth 2.1 como
mecanismo primario**, con autenticación por API token como alternativa **solo si el admin
de la organización la habilita explícitamente**, y que **el acceso siempre queda acotado a
los permisos existentes del usuario en Atlassian**, con controles de dominio que el admin
configura para decidir qué herramientas pueden conectarse — fuente:
[Atlassian Support — Authentication and authorization](https://support.atlassian.com/atlassian-rovo-mcp-server/docs/authentication-and-authorization/)
y [Atlassian Developer — Rovo MCP Auth Guide](https://developer.atlassian.com/cloud/rovo-mcp/guides/authentication-and-authorization/).

**Implicancia directa para Blocked #4** (el MCP `com.atlassian/atlassian-mcp-server`
encontrado en Orquestador con scope `/*`): el propio modelo oficial de Atlassian espera
scopes acotados y controles de admin explícitos — un scope wildcard **no está alineado con
la guía oficial de la propia plataforma**, lo cual **refuerza, con evidencia externa, la
prioridad de seguridad ya asignada a Blocked #4** en G3.2.5/G4.3. Esto no resuelve la
decisión bloqueada (sigue `REQUIRES VALIDATION` si el MCP encontrado usa OAuth 2.1 o API
token, y si el admin de MOA lo habilitó a propósito) — pero da un criterio externo
concreto contra el cual evaluarlo cuando se resuelva.
