# G4.1 — Product Architecture Baseline

**Fase**: G4.1. **Estado**: PROPOSAL en su totalidad, salvo citas FACT explícitas.
**Precondición**: G3.3 CLOSED (ver los 9 documentos de esta misma carpeta). Este documento
no reemplaza ninguno de ellos — los usa como base y diseña **cómo se operacionalizan**.
**No se implementó nada como consecuencia de este documento** — no se creó `registry/`, no
se creó ningún pipeline, no se creó ningún Agent/Skill/MCP real. Eso queda para G4.2+ con
autorización explícita (ver sección 21).

## Pregunta que este documento responde

> ¿Cómo debe construirse MOA-AI-Engineering para convertirse realmente en una capacidad
> interna reutilizable de AI Engineering, y no quedarse como un repositorio documental?

---

## 1. Executive Summary

G3.3 dejó una arquitectura conceptual sólida (9 documentos, revisados y corregidos) pero
—como la propia revisión final de G3.3 constató— **8 de 10 componentes del Common Core son
hoy exclusivamente documentación**, sin mecanismo operado. G4.1 no implementa esos
mecanismos — diseña **cómo deberían implementarse**, priorizando la opción más simple que
resuelve el problema (Principio #5), reutilizando lo que ya existe (Azure DevOps, git,
`moa-metrics`) en vez de proponer infraestructura nueva. La decisión de diseño central de
este documento: **el Registry v1 vive como archivos versionados en git dentro del propio
repositorio, no como base de datos ni servicio** — esto resuelve el bloqueo de Discovery
identificado en G3.3 sin construir nada nuevo, y es reversible/simple de migrar después si
se decide otra cosa.

## 2. Product Definition

**MOA-AI-Engineering no es un repositorio de documentación — es la implementación de
referencia de una capacidad de AI Engineering** (ya establecido en `operating-model.md`).
El "producto" tiene 2 tipos de consumidores:

- **Equipos consumidores** — descubren, adoptan, adaptan, ejecutan, evalúan, miden y dan
  feedback (Discovery + Adoption Model, secciones 8-9).
- **Quien gobierna el Common Core** — evalúa candidatas, aprueba promociones, mantiene
  Standards/Registry (Contribution Model, sección 10) — **rol sin confirmar, BLOCKED #1**.

**Alcance del baseline (v1, esta fase)**: diseñar el **mínimo mecanismo operativo** que
permite que el ciclo completo (Team-specific→...→Common Core→Discover→...→Improve) sea
ejecutable con herramientas que ya existen (git, PRs de Azure DevOps), sin depender de
decisiones bloqueadas para poder empezar con las capacidades de bajo riesgo.

## 7. Capability Registry Architecture

**Evolución de modelo documental a mecanismo operativo — decisión de diseño central de
G4.1:**

### Source of truth (PROPOSAL)

El Registry vive como **archivos versionados en git**, no como base de datos ni servicio
(consistente con `capability-registry.md`: "no se implementa base de datos ni servicio en
esta fase" — y con el Principio #5, preferir la arquitectura más simple). Propuesta:
`registry/entries/<id>.md` (o `.yaml`), un archivo por capacidad, con el schema de 27
campos ya definido en `capability-registry.md` (18 originales + 6 de G3.3 + 3 de G3.3
Corrections) como frontmatter/estructura. **No se crea esta carpeta en esta fase.**

### Schema

Reutiliza sin duplicar: los 27 campos de `capability-registry.md`. Este documento no
redefine el schema, define **cómo se llena y mantiene**.

### Ownership

**BLOCKED #1** — sin owner confirmado del Common Core, no hay quién administre el Registry
formalmente. Mitigación propuesta mientras tanto: cualquier equipo puede **proponer** una
entrada (ver Contribution Model, sección 10); solo la promoción a `Corporate Standard = Y`
requiere aprobación, que hoy recae de facto en el Solutions Architect de esta sesión
(FACT, no un rol organizacional confirmado a futuro).

### Lifecycle

Reutiliza `lifecycle.md` sin cambios — `Lifecycle State` (Capability Lifecycle) +
`Corporate Standard` (Adoption Status) son campos del Registry, no un modelo paralelo.

### Discovery, Status, Version, Provenance, Adoption, Evaluation, Metrics, Configuration
### Status, Real Use Status, Corporate Standard, Repository/Branch/Integration State

Todos ya son campos definidos en `capability-registry.md` — este documento no los
redefine. La novedad de G4.1 es el **mecanismo de población**:

1. **Entradas Team-Specific** (informativas, sin necesidad de Gate): cualquier equipo
   puede agregar una entrada describiendo su propia capacidad, con `Corporate Standard = N`
   por default. Esto resuelve Discovery sin esperar que nada complete el Gate — permite
   poblar el Registry con lo ya relevado (DataAgro, Scato Logística, Orquestador,
   `moa-sdlc`, `moa-metrics`) como punto de partida.
2. **Entradas candidatas a Common Core**: requieren pasar por el Assessment Gate (sección
   12) antes de que `Corporate Standard` pueda pasar a `Y`.

**Regla dura reafirmada**: `Configuration Status` y `Real Use Status` se completan de
forma independiente y con evidencia directa — nunca se infieren de `Evaluation Status` u
`Observability Status` (regla ya fijada en G3.3 Corrections, no se modifica acá).

## 8. Discovery Model

Cómo un equipo encuentra: qué existe, para qué sirve, quién la mantiene, si puede
adoptarla, qué riesgo tiene, qué evidencia existe, qué evaluación tiene, si es Corporate
Standard, cómo adaptarla — **todo esto son columnas del Registry** (sección 7). El
mecanismo de descubrimiento propuesto:

- **v1 (esta fase, sin tooling)**: navegar `registry/entries/` directamente en el repo (es
  texto plano versionado, buscable con grep/búsqueda de archivos — exactamente como se
  hizo en todo el relevamiento G1-G3.2.5).
- **v1.1 (PROPOSAL, no implementado)**: un archivo índice generado (`registry/INDEX.md`),
  agrupado por `Type`, `Team`, `Corporate Standard`, `Risk` — al principio mantenido a
  mano, candidato a generarse por script más adelante.

Esto cierra directamente el hallazgo de la Fase 5 (Adoption Test) de G3.3: "no hay
Registry poblado" — el mecanismo ahora existe en diseño; poblarlo es tarea de
implementación (sección 21), no de este documento.

## 10. Contribution Model

```text
Team → Candidate → Assessment → Evaluation → Validation → Common Core
```

| Rol | Quién | Estado |
|---|---|---|
| Quién puede proponer | Cualquier equipo (PROPOSAL — sin restricción evidenciada que lo impida) | PROPOSAL |
| Quién puede evaluar | **BLOCKED #1** — sin confirmar | BLOCKED |
| Quién puede aprobar | Solutions Architect (FACT para esta sesión) — ¿rol permanente de MOA? **REQUIRES VALIDATION** | Parcial |
| Quién mantiene | `Owner`/`Maintainer` del Registry — **sin ningún caso confirmado hoy** | REQUIRES VALIDATION |
| Quién puede retirar | Mismo cuerpo que aprueba — **BLOCKED #1** | BLOCKED |
| Evidencia mínima para ser "Candidate" | PROPOSAL: `Configuration Status = VERIFIED` + Use Case documentado + Value/Risk estimado (primeros 3 pasos del Capability Lifecycle) | PROPOSAL |
| Evidencia mínima para `Promote` | Las 14 dimensiones del Assessment Gate completas, con evidencia (no supuestos) | Ya definido en `assessment-gate.md`, sin cambios |

**Mecanismo propuesto (PROPOSAL, sin tooling nuevo)**: una Pull Request contra
`registry/entries/` = la acción de "proponer". Un reviewer (rol sin confirmar) aprueba la
PR = decisión registrada con trazabilidad nativa de git/Azure DevOps — **no se inventa un
sistema de aprobación nuevo**, se reutiliza el mismo flujo de PR que todos los equipos ya
usan (FACT, stack ya confirmado).

## 11. Lifecycle Integration — los 2 flujos completos, de punta a punta

### Flujo A — de Team-specific a Common Core (ilustrativo, hipotético — no es una decisión real)

```text
Team-specific (ej. skill "azure-devops-cli" en Scato Logística/Orquestador)
  → Candidate: se crea registry/entries/azure-devops-cli.md (Configuration Status=VERIFIED,
    Use Case documentado)
  → Assessment: se aplica el rubric de 14 dimensiones (assessment-gate.md) — este caso ya
    tiene una clasificación preliminar real de G3.3: "ADOPT, tras reconciliar versiones"
  → Evaluation: Human Evaluation de que el contenido reconciliado es correcto (pendiente,
    no hecho)
  → Measurement: (opcional en este caso, bajo riesgo)
  → Human Validation: decisión explícita del Solutions Architect
  → Corporate Standard = Y (Adoption Status del Registry)
  → Common Core: la entrada queda disponible para cualquier equipo
```

### Flujo B — de Common Core a otro equipo (ilustrativo)

```text
Discover: equipo nuevo (ej. MOA Operaciones) navega registry/entries/, encuentra
  azure-devops-cli.md con Corporate Standard=Y
  → Adopt: la usa tal cual
  → Adapt: (no necesario en este caso, es genérica)
  → Execute: la usa en su propio flujo de Azure DevOps
  → Evaluate: valida localmente que los comandos funcionan en su contexto
  → Measure: (si aplica una métrica común, ej. tiempo ahorrado en tareas de DevOps)
  → Feedback: si encuentra un caso no cubierto, abre PR actualizando la entrada existente
  → Improve: la mejora vuelve al Common Core, disponible para todos los adopters
```

**Ninguno de los 2 flujos se ejecutó realmente** — son la traza conceptual pedida, usando
un caso real y ya evidenciado (no inventado) como ilustración.

## 12. Assessment Gate Integration

**De documental a operativo, sin automatización completa** (instrucción explícita):
propuesta — el rubric de 14 dimensiones de `assessment-gate.md` se adjunta como
**checklist en la plantilla de PR** que propone una entrada a `Corporate Standard = Y`
(reutilizando `templates/use-case-template.md` como base, no un formulario nuevo). El
reviewer completa el checklist en la PR misma — la evidencia y la decisión quedan en el
historial de git, consultables después. **No hay scoring automático** (ya descartado en
G3.3, se mantiene).

## 13. Evaluation / Observability / Metrics Integration

Contratos conceptuales (sin código) entre ejecución del equipo → Evaluation →
Observability → Metrics → Registry:

| Contrato | Qué contiene | Actualiza en el Registry |
|---|---|---|
| **Evaluation Report** | Qué se evaluó, método (Human/Scenario/Regression — `evaluation-observability.md`), resultado, evaluador, fecha | `Evaluation Status` |
| **Observability Report** | Qué señales se capturaron (aunque sea manual: "revisamos N ejecuciones este mes"), hallazgos | `Observability Status` |
| **Metrics Report** | Referencia a un dato de `moa-metrics` o medición manual, con fecha | `Metrics` |

Las 3 son **independientes** (Principio #9, reafirmado) — ninguna se infiere de otra, cada
una se reporta por separado, cada una puede estar vacía mientras las otras no.

## 14. Team Adaptation Boundary

Sin cambios respecto a `operating-model.md` — reafirmado con el vocabulario de este
documento: **Common Core posee** el schema del Registry, el proceso del Gate, el formato
de Standards, la definición de Golden Paths, la política de Governance/Security, y el

contenido de sus Instructions/Skills/Agents, su repo, su ejecución, y su Evaluation/

modifique algo fuera de su propio repo para adoptar/adaptar/ejecutar.

## 15. Security Boundary

Sin resolver ninguna decisión bloqueada (instrucción explícita). Reafirmado desde
`security-governance.md`: el modelo de riesgo proporcional aplica igual a cualquier
capability que entre al Registry. **El caso Atlassian MCP permanece explícitamente
BLOCKED/pendiente de validación de seguridad** — no se le asigna `Corporate Standard`, no
se le asigna `Configuration Status` más allá de lo ya evidenciado en G3.2.5, y cualquier
entrada de Registry para MCP en general debe declarar identidad/autenticación/scope antes
de poder avanzar más allá de `Candidate` en el Capability Lifecycle. Fronteras: hoy,
credentials/identidad viven en cada equipo (no hay evidencia de un proveedor de identidad
centralizado) — el Registry registra **qué** identidad se usa (campo a completar), no
**gestiona** identidades.

## 16. Versioning Strategy

| Qué se versiona | Mecanismo propuesto | Diferenciado de |
|---|---|---|
| **Capability version** | Versionado semántico simple (`vMAJOR.MINOR`) del *contenido* de la capacidad — campo `Version` del Registry, ya definido | Repository version |
| **Repository version** | Cada repo de equipo ya tiene su propio historial de git — no es responsabilidad de `MOA-AI-Engineering` versionarlo | Capability version |
| **Configuration version** | El commit/hash de git del archivo específico (Instruction/Skill/Agent) — **se reutiliza el versionado nativo de git**, no se construye un sistema aparte | Capability version (la versión semántica es para humanos; el hash es la traza técnica exacta) |
| **Adoption state** | **No es una versión** — es el campo `Corporate Standard` + `Adopters` del Registry (Adoption Status de `lifecycle.md`). Un equipo puede estar adoptando la v1.2 mientras el Common Core ya define v1.3 | Explícitamente distinto de versión de contenido |

**Principio**: no construir un sistema de versionado nuevo — git ya lo resuelve para
Repository/Configuration version; el Registry solo necesita el campo semántico adicional
para Capability version, que es lo único que git no expresa naturalmente (un cambio menor
de redacción vs. un cambio de comportamiento).

## 18. Architecture Decisions

Decisiones de diseño tomadas en este documento (PROPOSAL, no corporativas):

1. El Registry v1 es archivos versionados en git (`registry/entries/`), no base de datos.
2. Existen 2 clases de entrada de Registry: Team-Specific (self-serve, sin Gate) y
   Common Core candidate (requiere Gate) — esta distinción no existía explícitamente antes
   de G4.1 y es lo que permite empezar a poblar Discovery sin esperar BLOCKED #1.
3. El Gate se operacionaliza como checklist adjunto a una PR, no como automatización.
4. El Contribution Model reutiliza el flujo de PR ya existente en Azure DevOps — no se
   propone tooling nuevo de aprobación.
5. El versionado reutiliza git nativamente para Repository/Configuration version; solo
   Capability version necesita un campo semántico adicional.
